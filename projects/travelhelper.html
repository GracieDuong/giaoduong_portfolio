Section 01 · Problem

The problem with travel booking today

Travel platforms don't help users decide — they hand them more data to sort through. The result is fatigue, abandonment, and fragmented planning across tabs.

The dataset here is behavioral, not numerical: user pain points in travel decision-making — choice overload, unclear system responses, payment failures, and no recovery path when things go wrong.
Pain point 01
Choice overload
Users spend 20–30 minutes comparing options across multiple tabs. Too many filters, too little guidance — leading to decision fatigue and drop-off.
Pain point 02
System dead-ends
When inputs are unclear or unsupported, most platforms silently fail or return no results. Users have no path forward and abandon the session.
Pain point 03
No human fallback
Requests that exceed the system's capability — complex itineraries, edge cases, failed payments — have no escalation path, increasing operational friction.
Section 02 · Analysis

From pain point to product response

Each user problem was mapped to its impact on experience and to a specific product or service design response.

User / Business Problem Impact on Experience Product / Service Response
Users feel overwhelmed by too many travel options Decision fatigue and slower booking decisions Guided conversational prompts: destination, budget, purpose — narrow down before surfacing options
Unclear or incomplete user inputs User frustration and drop-off risk Input validation + re-prompt flow — no silent failure, always an actionable next step
Payment failures during checkout Booking abandonment at final step Retry logic with a maximum of 3 attempts + alternative payment method suggestion
Lack of personalized recommendations Lower engagement and conversion Recommendation-based filtering via conversation, not keyword search bars
Requests beyond chatbot capability Increased operational friction, user distrust Human handover workflow — escalation path with context transfer, no dead-end
Section 03 · Workflow

BPMN workflow design

A two-pool BPMN workflow separates what the user does from what the system handles — making validation, retry logic, and escalation paths explicit.

01
Input validation before recommendations
Every user input is validated before the system generates results. Incomplete or ambiguous inputs trigger a structured re-prompt, not a dead-end or empty state.
02
Re-prompt loop instead of silent failure
When the system cannot process an input, it returns a specific re-prompt with context — guiding the user toward a valid input rather than returning nothing.
03
Payment retry logic (max 3 attempts)
Failed payments trigger a retry loop with a maximum of 3 attempts. After the third failure, the system suggests an alternative payment method before escalating.
04
Human escalation path with context transfer
Unsupported requests or repeated failures route to a human agent — with conversation context transferred so the user does not have to start over.
05
Positive closure — confirmation and email
Successful bookings are confirmed with a summary in-chat and an email receipt — closing the loop and reinforcing trust in the system.
Fig 1 — BPMN 2-pool workflow (User + TravelHelper System): validation, retry logic, human escalation, and recovery paths
Design decision: Splitting into two explicit BPMN pools (User + System) forced clarity on responsibility boundaries — what the user triggers vs what the system owns. This revealed gaps in error handling that a single-lane diagram would have missed.
Section 04 · Interface

Conversational interface principles

The chatbot UI was designed around three principles — applied consistently across every screen and interaction state.

Principle 01
Guided interaction
Each prompt gives the user a clear next action. Options are surfaced as quick-reply chips when possible — reducing typing and cognitive load at every step.
Principle 02
Conversational simplicity
Short, plain-language messages throughout. No technical jargon, no overwhelming option lists. The system speaks like a knowledgeable friend, not a search engine.
Principle 03
Emotional design
Friendly tone, progress feedback, and reassurance on error states. Users who encounter a problem feel helped, not stuck — reducing abandonment at difficult moments.
Fig 2 — Main conversational interface (Figma) showing guided prompts, quick-reply chips, and booking confirmation flow
Outcome of the design approach: By treating the chatbot as a decision-support tool rather than a search interface, every screen has a clear purpose — narrow the options, confirm the choice, or recover from a failure. No dead-ends remain in the final flow.
Section 05 · Conclusion

What this project demonstrates

This case study demonstrates the ability to translate behavioral pain points into structured workflows — not just wireframes. The BPMN approach forced explicit thinking about edge cases, error states, and escalation paths before any UI was designed.

The combination of product analysis (pain point → impact → response), process design (BPMN), and UX execution (Figma) reflects the kind of end-to-end thinking that applies directly to Product Analyst and Business Analyst roles where process design and service recovery matter.

The skills used here — structured problem decomposition, exception handling, workflow documentation, and user-centered communication design — transfer directly to data-driven product work in fintech, e-commerce, and service operations.
